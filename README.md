# 🎮 YORR Arcade

**노트북이 화면, 휴대폰이 컨트롤러**인 웹 미니게임 모음.
노트북에서 QR을 띄우고 폰으로 찍으면, 폰을 휘두르거나 기울여 게임을 조종한다.
게임 5종 · 요트는 **최대 6인 턴제 온라인**, 3종은 방 코드로 **온라인 1:1 대전**까지 된다.

**개인 프로젝트** · 1인 개발 · React + TypeScript + Three.js + Socket.IO
🔗 [Live](https://yorr-arcade.onrender.com/)

---

  이 저장소의 게임 로직·3D 렌더링·센서 입력이 원본으로 쓰였다.

## ✅ 이 프로젝트에서 검증한 것

앱 설치 없이 브라우저만으로 "폰이 컨트롤러가 되는" 구조가 실제로 굴러가는지
확인하는 게 목표였다. AI 코딩 도구로 게임 5종을 빠르게 찍어낸 뒤,
직접 만져야 하는 부분(물리 감쇠·센서 임계값·권위 모델)은 수치로 재서 잡았다.
그중 2종이 팀 프로젝트 YORR의 최종 라인업에 채택됐다.

- **센서 입력** — `DeviceMotion` 가속도에서 중력을 저역통과로 제거하고 히스테리시스로
  한 번의 휘두름이 여러 번 잡히는 걸 막았다. 입력 지연은 실측 편도 6~7ms.
- **직접 만든 강체 물리** — 라이브러리 없이 주사위를 굴리고, 500판 시뮬레이션으로 손맛을 수치로 맞췄다.
- **권위 모델 3종** — 게임 성격에 따라 서버 권위 / 호스트 권위 / 단순 중계를 나눠 썼다.
- **CI/CD** — 타입체크·빌드·통합테스트를 통과했을 때만 배포된다. Render의 Auto-Deploy는 일부러 껐다.
- **에셋 0** — 로고·텍스처·그림자·마스코트·QR까지 전부 코드로 그린다. 외부 이미지·폰트를 하나도 안 쓴다.

## 📱 폰을 컨트롤러로 쓰기

이 프로젝트의 중심 구조. 게임 화면은 노트북에만 그리고, 폰은 **센서 입력만** 보낸다.

```
[폰]  가속도/자이로 감지 ──ctrl:swing──▶ [서버]  같은 페어링 방으로 중계 ──▶ [노트북]  판정·렌더
        ▲                                                                        │
        └──────────────── ctrl:hit (진동 피드백) ◀───────────────────────────────┘
```

1. 노트북 허브에서 **[폰 연결]** → **QR 코드**가 뜬다
2. **폰 카메라로 QR을 찍으면 끝.** `?ctrl=CODE`로 열려 코드 입력 없이 바로 연결된다
   (QR을 못 찍는 상황을 위해 4자리 코드와 주소도 같이 띄운다)
3. 폰이 컨트롤러 화면으로 바뀐다. **노트북이 고른 게임에 맞춰 폰 UI도 같이 바뀐다**(`disp:game`)

**스윙 감지** — 가속도 크기가 **14 m/s²** 를 넘으면 스윙. 중력 성분은 저역통과로 빼고,
히스테리시스로 한 번의 휘두름이 여러 번 잡히는 것을 막는다 →
[useSwing.ts](client/src/games/pingpong/useSwing.ts)

**슬래셔 조준** — `DeviceOrientation`의 yaw·pitch를 0~1 좌표로 정규화해 ~35Hz로 전송

**지연 측정** — 왕복 ping 중앙값을 계속 재고, 25ms를 넘을 때만 화면에 경고를 띄운다 →
[latency.ts](client/src/net/latency.ts)

> 센서 API는 **HTTPS에서만** 동작한다. 그래서 로컬 개발도 https로 띄운다(아래 실행 방법).

### 요트만 폰이 "양방향"인 이유

다른 게임은 폰이 휘두르기만 보내면 되지만, 요트는 킵·점수 선택이 게임의 본체라
그것만으로는 결국 노트북 마우스를 잡아야 한다.
그래서 노트북이 화면 상태를 폰에 내려보내고(`disp:yacht`) 폰이 조작을 올려보낸다
(`ctrl:keep`·`ctrl:select`·`ctrl:score`·`ctrl:react`) → **폰만으로 한 턴을 끝낼 수 있다.**
폰이 스스로 판정하지 않고 노트북에 "요청"만 하므로 두 화면이 어긋나지 않는다.
규약: [ctrlProtocol.ts](client/src/games/yacht/ctrlProtocol.ts)

- **한 노트북에 폰 여러 대**를 붙일 수 있다 (퀵드로우는 2대면 폰끼리 결투)

### 아이폰에서 진동이 안 되는 문제

`navigator.vibrate`는 WebKit이 구현하지 않았고, iOS의 모든 브라우저가 WebKit이라
**아이폰 크롬도 마찬가지**다(브라우저를 바꿔도 안 됨).
그래서 진동에만 기대는 알림은 아이폰에서 기능이 통째로 사라진다.
요트의 "내 차례" 알림은 **진동 + 알림음 + 화면 플래시** 세 가지를 같이 준다 →
[feedback.ts](client/src/lib/feedback.ts)의 `feedbackTurn()`.
(iOS는 사용자 탭 안에서 `unlockAudio()`를 한 번 호출해 둬야 소리가 난다 —
폰 컨트롤러의 "연결하기"·"센서 켜기" 탭에서 미리 깨운다)

### 소리·진동 설정을 한 곳에 둔 이유

모든 화면 우측 상단 **⚙️**. 허브·게임·폰 컨트롤러 어디서 바꿔도 같은 스위치다
(값은 [feedback.ts](client/src/lib/feedback.ts)가 들고 localStorage에 저장).
게임마다 따로 두지 않는 이유: 같은 저장 키를 여러 화면이 각자 관리하면 서로 밟고,
"소리 꺼"는 게임 설정보다 기기 설정에 가까워서 게임마다 다시 끄는 건 짜증난다.

## 🎲 주사위 물리 — 결과를 먼저 정하고 물리로 되감기

**요트 다이스**의 주사위는 키프레임 애니메이션이 아니라 **직접 만든 강체 물리**로 굴린다.

나올 눈은 이미 정해져 있는데 물리는 그걸 모른다. 그래서 이렇게 푼다 —
화면에 안 그리고 한 번 굴려 본 뒤, 그 자세에서 목표 눈이 위로 오도록 주사위 눈을 다시 붙이고
(정육면체 대칭이라 궤적이 안 바뀐다) 되감아 진짜로 굴린다.
**마지막에 억지로 돌려 맞추는 스냅이 0.**

규칙(순수 계산)은 [physics.ts](client/src/games/yacht/physics.ts),
3D 무대는 [dice3d.ts](client/src/games/yacht/dice3d.ts).

### 500판 돌려서 손맛 맞추기

물리는 **노드에서 그냥 돌아가므로**(three의 수학만 씀) 눈대중이 아니라 재서 맞췄다.
500판을 돌려 "구르는 시간 · 알당 이동거리 · 반대쪽 벽까지 가는 비율 · 초반 회전"을 뽑는다.

| | 처음 | 조정 후 |
|---|---|---|
| 구르는 시간 | 1.08초 | **1.52초** |
| 알당 이동거리 (판 가로 2.6) | 1.43 | **2.58** |
| 반대쪽 벽 도달 비율 | — | **83%** |

던지자마자 멈추는 원인은 던지는 세기가 아니라 **감쇠**였다.

- **회전 체감은 최고 회전수가 아니라 "초반 0.6초의 평균 회전"이 정한다.** 감쇠가 세면
  순간 100rad/s를 찍어도 금방 죽어 오히려 느리게 느껴진다. 이동 감쇠와 회전 감쇠를
  따로 둬서 "오래 굴러가되 팽이처럼은 안 돌게" 맞췄다.
- **판 밖으로 날아가던 버그**: 보이는 테두리가 0.3뿐인데 벽 충돌을 그 높이까지만 봐서,
  세게 던지면 테두리를 넘어 밖으로 날아갔다 다시 들어왔다. 진입은 원래 테두리를
  넘어와야 하므로, **판 안에 들어온 뒤부터** 높은 벽을 세워 막았다 (500판 이탈 0).
- 화면은 120Hz 물리를 그대로 그리지 않고 **직전 스텝과 보간해서** 그린다
  (60Hz 화면에서 프레임마다 밟는 스텝 수가 2·3·2·1로 흔들려 떨림으로 보이기 때문).

## 📐 QR 코드를 직접 그리고 왕복 테스트한 이유

이미지 파일이나 외부 API 없이 만든다. 인코딩만 검증된 구현(`qrcode`)에 맡기고
**모듈 격자를 SVG path로 직접 그린다** → 크기 자유롭고 `innerHTML` 주입도 없다.
라이브러리는 QR을 띄울 때만 동적 import(별도 청크 10KB).

QR은 잘못 만들어도 화면에는 그럴싸한 격자가 보여서 **눈으로 검증이 안 된다.**
그래서 [test/qr.test.mjs](test/qr.test.mjs)에서 **다시 디코드해** 같은 문자열이 나오는지 확인한다
(인코더와 디코더가 서로 다른 구현이라 왕복 테스트가 의미를 갖는다).

노트북이 `localhost`로 열려 있으면 QR이 폰에서 자기 자신을 가리켜 실패하므로,
그 경우엔 QR 대신 "172.x 주소로 여세요" 안내를 띄운다.

## 🗂️ 서버가 다루는 방 5종 — 권위를 셋으로 나눈 이유

| 접두어 | 용도 | 권위 |
|---|---|---|
| `pair:` | 노트북 1대 ↔ 폰 N대 컨트롤러 페어링 | 중계만 |
| `room:` | 요트 다이스 — **최대 6인 턴제** | **서버** |
| `pp:` · `rt:` · `rx:` | 핑퐁 · 리듬탭 · 퀵드로우 온라인 1:1 | 호스트 |

- **온라인 1:1**은 **호스트가 권위를 갖고** 시뮬레이션을 돌려 상태를 중계하고,
  게스트는 수신 사이를 추측항법으로 보간한다. 서버는 규칙을 모르고 중계만 한다.
- **요트 방(`room:`)은 서버가 권위를 갖는다.** 턴제·관전 때문이다 —
  주사위를 서버가 굴려야 6명 화면에 같은 눈이 뜨고, 점수 계산도 서버가 해서
  클라가 보낸 숫자를 믿지 않는다. 좌석 id는 `p1`~`p6`으로 고정하고,
  재접속은 입장 때 발급한 비밀 `token`으로 원래 자리를 되찾는다.

방 상태는 서버 메모리에만 있다(재시작 시 초기화).

## 🚀 실행하기

### 사전 준비물

- **Node.js 18+**
- 테스트용 스마트폰: **갤럭시(Chrome)** 또는 **아이폰(Safari)**
- 여러 명 테스트하려면 폰이 여러 대 (또는 PC 브라우저 여러 탭)

### 방법 ① 원클릭 (추천)

- **같은 와이파이/핫스팟**에서 플레이 → **`로컬플레이.bat`** 더블클릭
  - 서버(3001) + 웹(5173, https)이 뜨고, 폰 접속 주소(`https://172.20.10.x:5173/`)가 표시됨
- **멀리 있는 친구와 온라인** 플레이 → **`온라인플레이.bat`** 더블클릭
  - 빌드 후 서버가 앱+소켓을 서빙하고, ngrok 공개주소를 발급 → 그 주소를 공유
- (`.ps1`을 직접 우클릭 실행하면 Windows 실행정책 때문에 창이 닫힐 수 있어, 반드시 `.bat`을 쓰세요)

### 방법 ② 터미널 2개 직접

```bash
# 터미널 1 — 실시간 서버
cd server
npm install      # 최초 1회
npm run dev      # 포트 3001

# 터미널 2 — 웹(클라이언트)
cd client
npm install      # 최초 1회
npm run dev      # https://localhost:5173
```

> 웹(5173)은 `/socket.io` 요청을 서버(3001)로 **프록시**합니다(`vite.config.ts`).
> 덕분에 폰은 **5173 한 포트만** 열면 실시간 통신까지 됩니다. (CORS/추가 포트 불필요)

### 폰이 접속 안 될 때 (핫스팟)

학교/회사 와이파이는 **기기 간 통신을 막아서(AP 격리)** 폰↔PC 접속이 안 될 수 있습니다.
**폰 핫스팟**을 쓰는 게 가장 확실합니다.

1. 폰에서 개인용 핫스팟 켜기 → 2. 노트북 Wi-Fi를 그 핫스팟에 연결 →
3. 실행 스크립트 실행 후 뜨는 `https://172.20.10.x:5173/`를 폰 브라우저에 입력 →
4. 인증서 경고 → 계속 진행 (아이폰: "세부사항 → 웹사이트 방문")

> 💾 폰↔노트북 통신은 핫스팟 로컬 링크 안에서만 오가고 셀룰러를 안 탑니다.
> 게임도 노트북이 로컬로 서빙하므로 **플레이 중 데이터 사용은 사실상 0**입니다.

## ☁️ 배포와 CI/CD

**서비스 하나만 배포하면 된다.** Node 서버가 빌드된 앱(`client/dist`)과 소켓을 같은
포트로 서빙하므로, 클라이언트의 `io()`(주소 없이 = same-origin)가 그대로 동작하고
CORS 설정도 필요 없다. 프론트를 따로 올리면 이 구조가 깨진다.

```bash
npm run build   # client 의존성 설치 → 앱 빌드 → server 의존성 설치
npm start       # 서버가 앱 + 소켓을 PORT로 서빙
npm test        # 서버를 띄워 소켓 여러 개를 붙이는 통합 테스트
```

### 배포 흐름

```
develop 작업 ─PR─▶ CI(빌드+테스트) ─통과─▶ main 머지 ─▶ CI 재검사 ─통과─▶ Render 배포
                        │                                    │
                      실패 → 머지 못 함                    실패 → 배포 안 함
```

- **CI** = 타입체크·빌드·통합테스트 ([.github/workflows/ci.yml](.github/workflows/ci.yml))
- **CD** = 그게 통과했을 때만 Render Deploy Hook을 호출
- Render의 Auto-Deploy는 **일부러 껐다**(`autoDeploy: false`). Auto-Deploy는 push만
  보고 CI 결과를 모르기 때문에, 켜 두면 테스트가 빨간불인 커밋도 배포된다.

### 깨졌을 때

| 어디서 깨지나 | 어떻게 되나 |
|---|---|
| CI 검사 실패 | **배포가 아예 안 돈다.** 이미 배포된 버전이 그대로 서비스됨 |
| Render 빌드 실패 | Render가 새 버전을 안 띄우고 **이전 버전을 계속 서빙** |
| 배포는 됐는데 버그 | 자동으로 안 잡힌다 → 아래 롤백 |

앞의 둘은 "롤백"이 아니라 **애초에 안 바뀌는 것**이다. 진짜 롤백이 필요한 건 세 번째뿐.

```bash
# 방법 ① git으로 되돌리기 (권장 — 히스토리에 남고 CI를 다시 통과한다)
git revert <문제커밋> && git push origin main

# 방법 ② 급할 때: Render 대시보드 → Deploys → 이전 배포의 "Rollback"
```

### 무료 플랜에서 알아둘 것

- **인스턴스를 늘리면 안 된다.** 방 상태(`rooms` Map)가 프로세스 메모리에 있어서,
  2개로 늘리면 서로 다른 인스턴스에 붙은 사람끼리 같은 방을 못 본다
  (증상: 코드를 맞게 넣었는데 "방을 찾을 수 없어요"). 키우려면 Redis 어댑터가 먼저다.
- **유휴 상태로 두면 잠든다** → 첫 접속이 수십 초 걸린다(cold start).
- **재시작하면 진행 중인 방이 사라진다**(메모리 저장).

### 처음 한 번만

1. [Render](https://render.com) 가입 → **New → Blueprint** → 이 저장소 선택
   (루트의 [render.yaml](render.yaml)을 읽어 자동 설정된다)
2. 대시보드 → **Settings → Deploy Hook**의 URL 복사
3. GitHub 저장소 → **Settings → Secrets and variables → Actions** →
   `RENDER_DEPLOY_HOOK_URL`로 등록
4. 발급된 `https://<이름>.onrender.com` 주소를 공유하면 끝

## 🕹️ 요트 다이스 — 최대 6인 턴제 온라인 플레이

> 나머지 4종은 허브에서 카드를 눌러 바로 시작한다. 조작은 각 게임 시작 화면에 안내가 뜬다.

허브에서 요트 카드를 누르면 **[방 만들기] · [게임 참여] · [혼자 하기]** 를 고른다.

1. **방 만들기** → **6자리 초대 코드**가 발급되고 바로 대기실에 들어간다.
   참가자는 **[게임 참여]** 에서 그 코드를 넣으면 입장 (`?room=CODE` 링크로도 바로 입장)
2. **대기실**: 좌석 6칸이 보인다. 코드를 탭하면 복사. 다 모이면 방장이 **[게임 시작]**
3. **게임 (턴제)**: 보드는 화면에 하나뿐이고 **지금 차례인 사람의 주사위를 모두가 같이 본다.**
   - 내 차례: **[굴리기]**(또는 폰 흔들기) → 남길 주사위를 **탭해 KEEP 레일로 올림** → 나머지만 다시 굴림 (**최대 3번**)
   - **점수표에서 칸을 고르고**(금색 = 지금 넣으면 몇 점) 아래 **큰 버튼으로 확정** — 오탭으로 칸을 날리지 않게 2단계
   - 남의 차례: 조작이 잠기고 **관전**. 굴러가는 주사위 · KEEP · 점수판이 실시간으로 따라온다
   - 요트·라지 스트레이트 같은 **족보 콜아웃**은 방 전체에 같이 뜬다
   - **차례당 45초.** 시간을 다 쓰면 서버가 대신 굴리고 **가장 점수가 높은 칸**에 기록한다
     (한 사람이 폰을 놓고 가도 판이 멈추지 않는다. "시간초과·자동"으로 표시됨)
   - 리액션 버튼(👍😂😮👏🎉)으로 남의 차례에도 참견할 수 있다
4. **결과**: **12라운드 × 인원**을 다 채우면 총점 순위. 1등은 금색, 각 줄에 "제일 크게 먹은 칸"도 표시.
   방장이 **[다시 하기]** 를 누르면 같은 방으로 대기실로 돌아간다

**연결이 끊겨도 자리를 지킨다.** 폰이 잠기거나 새로고침해도 입장 때 받은 토큰으로
원래 좌석·점수판을 그대로 되찾는다. 그동안 내 차례가 오면 서버가 8초만 기다린 뒤 대신 플레이한다.

### 📖 점수 규칙 (한국에서 통용되는 요트다이스 룰)

윗줄:
- **1~6**: 해당 눈의 합 (예: `4`는 4가 나온 개수 × 4)
- **보너스**: 윗줄(1~6) 합이 **63점 이상**이면 **+35점**

아랫줄:

| 족보 | 조건 | 점수 |
|------|------|------|
| 초이스 | 아무 조합 | 주사위 5개 합 |
| 포카드 | 같은 눈 4개 이상 | 주사위 5개 합 |
| 풀하우스 | 3개 + 2개 | 주사위 5개 합 |
| S.스트레이트 | 4개 연속 | 15점 |
| L.스트레이트 | 5개 연속 | 30점 |
| 요트 | 5개 모두 같음 | 50점 |

> 1938년 원조 Yacht 룰과 한국식(야찌 보너스 포함) 룰에 차이가 있어, 한국 플레이어에게
> 익숙한 방식(스몰/라지 스트레이트 · 윗줄 63점 보너스)을 채택했습니다.
> 규칙은 [game/yacht.ts](client/src/game/yacht.ts) 한 곳에 모여 있어 쉽게 바꿀 수 있습니다.
